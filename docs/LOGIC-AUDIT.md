# 518.PLUS 全局逻辑审计与闭环计划

> 2026-08-26 · 依据：生产库实查 + 全代码链路审读 · 目标：归类全部业务逻辑，逐项判定缺失，逐一闭环，不留分叉不留敞口

## 〇、核心结论（先看这个）

**账务模型有一处根本性混乱：收益（provider_earn）与积分余额共用一个池子。**

实证（生产库用户 ern80797）：
```
total = 300 = provider_earn(+500) + withdraw(-200)
```
提供者赚的积分直接进入消费余额；提现从"总池"扣减。后果：
- 用户看不懂："我赚了 500，为什么只显示 300？"（被提现扣走了，但积分页没有任何解释）
- **消费会侵蚀可提现额度**：赚 500 → 花 300 消费 → 只能提 200。等于用户花自己的血汗钱
- 积分页（消费视角）和收益页（供给视角）是**同一个池的两张假面**，"分列"只是 UI 装饰

这与既定红线"面值账+现金成本账分轨、赠送额度不参与分账"同源但更严重：不只是账本内部口径，是用户可见的资金语义混乱。

## 一、全局逻辑归类（全部业务域 → 现状 → 缺口 → 处置）

### A. 账务域（最严重，先闭环）

| # | 逻辑 | 现状 | 缺口/敞口 | 处置 |
|---|---|---|---|---|
| A1 | **双池分离**：消费积分池 vs 收益池 | 同一 ledger 池，kind 区分 | 收益可被消费侵蚀；两页语义假分离 | **核心改造**：available_to_withdraw 只由 provider_earn−withdraw 派生（已是），但必须**禁止消费扣减越过赠送+充值额度**（consume 只能动 gift/topup，不动 earn）→ 账本加"可消费余额"派生函数 |
| A2 | 积分页流水 | ledger 全 kind 混显（含 provider_earn/withdraw） | 用户在积分页看到"收益+500/提现-200"与消费记录混排，无法理解 | 积分页只显消费侧流水（grant/consume/refund/topup）；收益流水只在收益页 |
| A3 | 充值入口 | plans/packages 表+支付字段全在，**零数据零订单**，用户面不存在 | 会员制=纯骨架 | 短期：积分页"充值"区块列出 packages（管理员录入后即活）；支付未接前显示"联系管理员/预留"占位。**不造新分叉**：只激活既有表，不加新概念 |
| A4 | 提现通道 | withdrawals 全流程已闭环（申请/批准/凭证） | 已闭环 | 无 |
| A5 | 注册赠送 | activities 表 signup(100) active，注册静默发 | **零暴露**：注册页/首页无任何"送100积分"宣传 | 注册页+登录页提示"新用户注册送 100 积分"（从 activities 表读，硬编码禁止——活动数据化铁律） |

## 二、本轮闭环清单（按序执行，每项验收+回归）

1. **A1 双池分离**：`spendable_balance()` —— consume 只能扣 grant/topup 部分；provider_earn 仅可提现。余额展示双数字（积分余额=可消费，收益页=可提现）
2. **A2 流水分列**：积分页流水过滤 kind IN (grant_*, consume, refund, adjust, topup)；收益页已有 revenue_lines
3. **A5 注册赠送暴露**：注册页横幅"注册即送 100 积分"（读 activities 表）
4. **D1 充值区块**：积分页充值卡（packages 列表+状态，数据空时显示"充值即将开通"）
5. **B3 调用记录**：工具卡片"记录"按钮 → 最近 20 条 tool_calls
6. **B6 接入契约文档**：发布工具页折叠区

## 三、不做（避免分叉）

- 不做 B4 健康探活（需定时基建，单列后续）
- 不动 plans/packages 表结构（D1 只激活不重构）
- 不新增任何"会员等级"概念（用户未要求）
